# Release controls and acceptance

FinBuddy integrates through protected `preprod` and promotes through a PR from `preprod` to protected `main`. Both branches retain zero mandatory independent reviewers. The checks and the release-owner acceptance receipt supply the evidence for an authorized release. The owner's [22 November consolidation decision](firebase-consolidation.md) in [#184](https://github.com/theharithsa/finbuddy/issues/184) supersedes the earlier two-project layout. [Issue #172](https://github.com/theharithsa/finbuddy/issues/172) tracks these controls; [#174](https://github.com/theharithsa/finbuddy/issues/174) owns rehearsal and [#169](https://github.com/theharithsa/finbuddy/issues/169) owns production telemetry acceptance.

## Candidate and promotion

Both protected branches require an up-to-date PR. Before starting a new candidate, check `git merge-base --is-ancestor origin/main origin/preprod`. If the previous production merge is missing, create a branch from current preprod, merge current main into it, and open a PR back to preprod. Merge that PR with a merge commit so Git retains the production parent. Build and accept the resulting preprod commit before opening the next promotion. The GitHub Update branch button cannot write directly to protected preprod.

The [application workflow](../.github/workflows/finbuddy.yml) checks foundation contracts, web lint/unit/browser behavior, API contracts/emulators, and the historical Functions build. All three package trees have an audit gate. PR jobs receive no cloud identity or Dynatrace ingest credential.

A trusted push to `preprod` builds the pre-production and production web bundles from the same source, using the shared Firebase configuration and each environment's RUM configuration. The `finbuddy-release-<attempt>` artifact contains both bundles and a schema-2 receipt with the shared project, exact pre-production site, both data roots, source SHA, Git tree, CI run and attempt, creation time, and SHA-256 directory digests for both bundles and the API source. Retention is seven days; acceptance expires after 24 hours. A workflow rerun changes its attempt and requires a full rebuild and fresh acceptance. Verification artifacts also include the attempt so earlier failure/recovery reports remain available.

The first deployment of the reviewed retry-enabled audit function uses Firebase's explicit non-interactive confirmation only within the selected backend codebase; no unrelated functions are selected. The pre-production deployment checks the artifact, deploys only the `finbuddy-api-preprod` backend codebase and Hosting, then runs live health, denial, synthetic API/browser and shared-project client/API boundary checks. It records previous and deployed provider release identities and effective traffic allocations. Before Hosting cutover, each backend must have the checked source and dedicated identity; deployment explicitly routes 100% of traffic to that exact revision and reads the allocation back. Cloud Run preserves earlier rollback allocations across subsequent deployments, so a deployed revision alone does not prove it is serving. The old callable source in `/functions` is built and audited but is never selected by this deployment.

Before promotion, the release owner completes the independent fresh Dynatrace and recovery checks in #174 and records `preprod-acceptance` on the exact source commit. Its description binds the successful staging run, attempt and SHA-256 of `receipt.json`. Publish success only after the required checks pass; publish failure to withdraw acceptance. This status is an operational test receipt, not a request for a second reviewer.

The `promotion` check accepts only a same-repository PR from `preprod` to `main`, the latest successful owner receipt, and a completed successful push run from the exact application workflow. It downloads the identified artifact and rechecks its hashes, age, source tree and API source. Missing/failed acceptance, forks, wrong workflow/project, source changes, stale/rerun evidence, modified artifacts and a different promotion merge tree fail the gate. Regression tests in [release-control.test.mts](../tests/release-control.test.mts) exercise these failures.

On a `main` push, the gate resolves the actual merged promotion PR and repeats verification before cloud authentication. Production deploys the API/audit prerequisites and the exact production web artifact from the accepted run. The web marker and backend `FINBUDDY_BUILD_COMMIT` identify that accepted source; the distinct GitHub promotion merge SHA is retained in the run. Pages builds from the accepted source and records the same revision after live checks pass.

## Deployment identity and secrets

| Environment | Firebase project | Hosting target | Firestore root | GitHub environment | Branch |
| --- | --- | --- | --- | --- | --- |
| Pre-production | `finbuddy-2025` | `preprod` | `preprod/data` | `pre-production` | `preprod` |
| Production | `finbuddy-2025` | `prod` | `prod/data` | `Production` | `main` |

Both environments share Firebase Auth and the receipt bucket. Server configuration must explicitly select `prod` or `preprod`. Separate backend names, runtime service accounts and exact Hosting targets prevent accidental co-deployment. Pre-production uses `finbuddy-release-preprod`/`finbuddy-runtime-preprod`; production uses `finbuddy-release`/`finbuddy-runtime-prod`. GitHub WIF binds the immutable repository-ID subject, branch, environment and workflow. No service-account keys are created.

Firestore Admin SDK IAM is project-wide and bypasses client rules; it does not establish collection-level isolation. The bucket retains its existing fine-grained configuration. Rules and API authorization enforce environment/owner boundaries, including rejection of pre-production synthetic identities at production and FinVision paths. Test these real endpoints; do not reuse the former cross-project IAM-denial claims. Keep act-as grants scoped to the selected runtime and required build/default identities. Preserve unrelated services and FinVision.

Secret Manager holds `FINBUDDY_PREPROD_DT_INGEST_AUTHORIZATION` for pre-production and `FINBUDDY_DT_INGEST_AUTHORIZATION` for production. Each runtime gets access to its intended secret only. The owner expressly authorized the configured India CS MCP credential for production; store it without displaying it and verify actual ingestion. Do not delete or silently rotate existing CI/legacy secrets. The Thoth observer keeps its separate configuration.

Only `FINBUDDY_PROD_API_KEY` is needed for the shared public Firebase configuration in hosted tests. `FINBUDDY_PREPROD_RUM_URL` and `FINBUDDY_PROD_RUM_URL` remain distinct. Browser analytics stays opt-in with replay disabled. Approved pre-production accounts have the explicit access claim; synthetic test accounts are marked as pre-production and denied production access. Both sites support the shared Google provider. FinVision's existing Hosting site, identity and collection contracts remain in place.

## Live tests, recovery and evidence

Firestore and Storage policies are independent prerequisites. Deployment reads both release/ruleset identities and compares normalized source digests before application changes. Pre-production accepts either the exact reviewed transitional policy or the strict final policy. Production requires strict policy. The transition preserves legacy production owner access and FinVision while the verified copy is prepared. Cutover follows the private snapshot, receipt reconciliation, resumable copy and source-set verification in the [consolidation guide](firebase-consolidation.md); source, policy, copy and live application acceptance remain distinct. A direct Storage ownership failure blocks acceptance even if the REST receipt endpoint is owner-scoped.

[live-acceptance.mts](../scripts/live-acceptance.mts) requires an explicitly selected environment and `FINBUDDY_ALLOW_SYNTHETIC_WRITES=true`. It creates random accounts with the `finbuddy-release-` UID prefix and `example.test` addresses. Credentials remain in process memory and are never uploaded. Pre-production verifies its Firebase credentials cannot reach production Firestore/Storage and its personal API credential is rejected by production. After the new production backend is live, production additionally verifies rejection of a preprod-only sign-in session. Each Storage probe uses Firebase's actual ID-token header rather than an invalid transport credential.

The API suite verifies each resource, bill-payment idempotency, summaries, owner denial, receipt rules, token scopes/expiry/revocation and a synthetic record-plus-receipt restore. Desktop/mobile browser checks exercise sign-in, expense edits/persistence/deletion, navigation, appearance, Developer Options, token revocation, a signed-in recurring deposit preview/save/reload/remove journey and opt-in RUM. Cleanup runs in `finally`, is restricted to those fixture identities, and gates success.

Reports under `verification/` contain only bounded scenario IDs, outcomes, revision/probe markers, provider identities and cleanup results. Keep them separate from an interactive Google-provider sign-in, emulator evidence and independent tenant searches. Do not describe a RUM tag load as proof of a searchable action, or a successful ingest response as a tenant query result.

Before release, preserve the preceding Hosting version, API/audit source, environment configuration and rules/index identities. Rehearse component rollback in pre-production and restore the candidate; recheck its served source and denials afterward. Never restore old source over a schema it cannot read, including non-expiring tokens. There is no destructive automatic household-data rollback. Synthetic record/file restoration does not establish backup coverage for customer data; verify provider coverage separately before a data migration. This delivery changes the document paths while preserving financial field types and IDs. Do not roll an old-schema application back over new writes without reconciliation.

Attach the successful run/attempt, candidate receipt digest, provider revisions, live scenario results, fresh signal-query evidence, recovery result and cleanup to #174 and #169. Changes after acceptance require affected checks again. See the [release and rollback guide](release-plan.md), [observability contract](observability.md) and [reviewed backlog plan](preproduction-plan.md).
